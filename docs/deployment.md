# Deployment

The same three Helm charts run on a laptop (k3d) and on a server (k3s). Only the
values files differ.

| Chart | Namespace | Contents |
| --- | --- | --- |
| [`charts/store`](../charts/store) | `store` | WordPress, MariaDB, the WP-CLI setup Job, woo-mcp |
| [`charts/upstreams`](../charts/upstreams) | `upstreams` | `everything` and `toolbox` MCP servers |
| [`charts/platform`](../charts/platform) | `platform` | gateway (with the dashboard) and Postgres |

Install order matters once: the platform chart copies the upstream tokens out of the
other two namespaces' Secrets, so `store` and `upstreams` go first. `make install`
does that.

## Local (k3d)

Requirements: Docker with about 4 GB of memory, `kubectl`, `helm` 3.14+ or 4,
`k3d` 5.7+, Node 22+, `pnpm` 9+ and `jq`.

```bash
./scripts/quickstart.sh
```

It checks the tools, creates the k3d cluster if it is missing, builds and imports the
images, installs the three charts, and prints the URLs and the generated admin
passwords. The same steps by hand:

```bash
pnpm install
make cluster     # k3d cluster "urumi", ports 80/443 on localhost
make up          # typecheck, build 4 images, import them, install the charts
make e2e         # 82 end-to-end checks against the cluster
```

| What | Where |
| --- | --- |
| Storefront | http://store.127.0.0.1.nip.io |
| WooCommerce admin | http://store.127.0.0.1.nip.io/wp-admin (user `admin`) |
| Dashboard | http://app.127.0.0.1.nip.io (`admin@urumi.local`) |
| MCP endpoint | http://app.127.0.0.1.nip.io/mcp |

```bash
kubectl -n store get secret wordpress -o jsonpath='{.data.admin-password}' | base64 -d     # WooCommerce admin
kubectl -n platform get secret gateway -o jsonpath='{.data.admin-password}' | base64 -d   # dashboard admin
```

**Local domains.** `*.127.0.0.1.nip.io` is public wildcard DNS that answers
`127.0.0.1`, and k3d publishes Traefik on ports 80 and 443 of localhost, so no
`/etc/hosts` edits are needed. Without internet DNS, add `store.127.0.0.1.nip.io`
and `app.127.0.0.1.nip.io` to `/etc/hosts`.

**Chat agent.** Put an OpenAI-compatible key in a gitignored file, then reinstall:

```bash
printf 'llm:\n  apiKey: "sk-or-..."\n' > values-secrets.yaml
make install
```

The default provider is OpenRouter with `anthropic/claude-haiku-5.5`; change
`llm.baseUrl` and `llm.model` in [`charts/platform/values.yaml`](../charts/platform/values.yaml)
for any other OpenAI-compatible API.

**Stop and resume.** `k3d cluster stop urumi` keeps all data; `k3d cluster start urumi`
brings it back.

## Server (k3s)

> This path has been rendered with `helm template`, not yet installed on a public VPS.

1. **Cluster.** On the server: `curl -sfL https://get.k3s.io | sh -`. It ships Traefik
   and the `local-path` storage class, the same as k3d. Open ports 80 and 443.
2. **TLS.** Install cert-manager and create a `ClusterIssuer` named
   `letsencrypt-prod` using the HTTP-01 solver with ingress class `traefik`.
3. **DNS.** Point `store.<domain>` and `app.<domain>` at the server. `<ip>.sslip.io`
   works as a domain with no DNS setup.
4. **Images.** Build for the server's CPU and push to a registry it can reach:
   `docker buildx build --platform linux/amd64 -f docker/gateway.Dockerfile -t <registry>/gateway:<tag> --push .`
   (likewise `woo-mcp`, `toolbox-mcp`, `everything`).
5. **Values.** In each chart's `values-prod.yaml`, set `global.domain` and the image
   repositories (`wooMcp.image.repository`, `servers.everything.image.repository`,
   `servers.toolbox.image.repository`, `gateway.image.repository`). Put the LLM key in
   `values-secrets.yaml`.
6. **Install**, with the server's kubeconfig as the current context:

```bash
make install VALUES=prod CONTEXT=<context> TAG=<tag>
```

### What changes between local and production

| Concern | `values-local.yaml` | `values-prod.yaml` |
| --- | --- | --- |
| Domain | `127.0.0.1.nip.io` | your domain |
| TLS | off | cert-manager `letsencrypt-prod`; Ingress gets a `tls` block; cookies become `Secure` |
| Storage | `local-path`, 2 Gi | `local-path` on one node, 10 Gi; another class via `global.storageClass` |
| Images | built locally, imported into k3d | pulled from a registry (`pullPolicy: Always`) |
| Replicas | 1 | 2 for the gateway and woo-mcp, which hold no state |
| Secrets | generated in the cluster; LLM key from a gitignored file | the same |

## Secrets

Every credential is generated by Helm in the cluster on first install, read back with
`lookup` on every upgrade so it never changes, and kept on uninstall
(`helm.sh/resource-policy: keep`), because the volumes outlive a release and the
passwords inside them must too. Nothing secret is in the repository or a values file.

| Secret | Keys |
| --- | --- |
| `store/mariadb` | `root-password`, `password` |
| `store/wordpress` | `admin-password` |
| `store/woo-rest` | `consumer-key`, `consumer-secret` |
| `store/woo-mcp` | `bearer-token` |
| `upstreams/toolbox` | `api-key` |
| `platform/postgres` | `password` |
| `platform/gateway` | `admin-password`, `session-secret`, `encryption-key`, `llm-api-key`, `seed-servers` |

## Upgrade and roll back

Each chart is its own release, so the store, the upstreams and the gateway upgrade
separately.

```bash
make up                                              # images are tagged by a hash of their sources
helm history store -n store
helm rollback store <revision> -n store
```

- `make up` tags images with a hash of their sources, so a changed component gets a
  new tag and Helm restarts exactly that component.
- The store's setup Job runs after every install and upgrade and only changes what
  differs.
- The gateway applies database migrations at start, under a lock so replicas take
  turns. Migrations only add, so the previous image still runs after a rollback.
- Volumes and generated Secrets survive upgrades, rollbacks and uninstalls.
